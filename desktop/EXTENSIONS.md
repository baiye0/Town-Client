# 社区插件扩展方案

状态：设计提案，2026-09-11。本文定义后续实现方向；客户端尚未提供这里提出的插件 SDK、界面扩展加载器或统一插件管理页。当前可用的是本地 Portal Kit 导入和 Grove Kit 安装。

目标是让社区作者通过稳定接口交付扩展，用户在客户端发现、配置、使用和管理它们，普通插件更新无需重新发布客户端。继续使用一段 Being 对话和既有 Loom / Town / Portal 协议。插件不能凭自身的声明启用尚未实现或未开放的能力。

## 已有基础与缺口

| 部分 | 当前代码 | 需要补齐的内容 |
| --- | --- | --- |
| 社区工具分发 | [kit-install.ts](kit-install.ts)：Grove 下载、安装预览、依赖安装和 MCP 预检查 | 发布者和来源记录、版本锁定、升级与回退 |
| 本地插件开发入口 | [kits.ts](kits.ts)：目录导入、manifest 校验、平台判断 | 示例模板、完整开发文档、离线校验工具 |
| 工具运行 | Rust Portal 的 Kit / MCP 运行时 | 在客户端准确呈现运行状态与归属，不另起重复运行时 |
| 配置与认证 | Portal manifest 的 `provision.env` / `provision.auth` | 通用配置表单和登录说明，按提供方呈现未支持的流程 |
| 插件界面 | 目前没有社区界面扩展加载器 | 版本化的声明式面板和数据接口 |
| 编排适配器 | 目前没有 Worker 运行时 | 作为独立的可选扩展阶段，仍需明确产品范围 |

Rust 现有能力见 [Kit 配置与热加载](../heart-portal/docs/kit-configuration.md) 和 [manifest 类型](../heart-portal/portal/src/kits/manifest.rs)。`permissions` 元数据不等于操作系统强制隔离，`healthy` 也不代表第三方账号授权充分。客户端需要分别展示配置、进程、连接与操作结果。

## 扩展类型

### 工具插件：沿用 Portal Kit

社区工具继续提供原有 `manifest.json` 和 stdio MCP 服务，由 Portal 注册与调用。保留现有工具命名和路由规则，不要求服务端新增插件接口。客户端负责安装、配置与状态呈现。

纯 MCP 服务仍需补齐 Portal Kit 所需的启动命令、工具定义及配置说明。不能因为支持 MCP 就声称可以直接导入所有 Codex 插件、远程 MCP 服务或其 UI。

安装目录、Portal 名称和配置来源必须一起记录。用户手工配置或其他客户端共享的 Kit 标为“外部管理”；不能用一个本地启用开关假装已经停止了独立 Portal 中的工具。对客户端管理的 Kit，停用、升级或卸载必须由实际拥有进程的 Portal 完成撤销工具和在途调用处理，收到确认后才显示已停用；该控制尚未实现时只展示状态。

### 界面插件：先提供声明式组件

首批支持列表、详情卡片、筛选项、设置表单和导航入口。例如，社区作者可以为公开卷轴提供按类型筛选的阅读面板，无需自行实现鉴权、网络请求或消息同步。

插件声明要呈现什么；宿主用统一组件渲染，并通过已实现的类型化数据操作读取数据。避免依赖客户端内部 DOM、CSS 类名或 Electron IPC。主题、字号、键盘操作、加载和错误状态由宿主统一处理。

数据操作按实际服务能力逐项开放。第一版仅开放明确列出的读取操作，个人卷轴、私信和历史正文不是默认可见数据。写入界面后续也应调用现有服务端接口和宿主的发送流程，保留接收对象、可见范围及失败草稿，不能让插件后台静默发送。

确有复杂交互需要时，再增加隔离的网页面板。它需要独立来源、受限消息通道、请求大小与频率限制、生命周期撤销和经验证的渲染器隔离。现有浏览器的持久登录会话不能直接复用为插件会话；网页也不能取得主窗口 preload 或 Being token。没有完成这些条件前不开放任意插件 JavaScript。

### 工作流说明与执行适配器

插件可以携带 README、示例和使用说明；第一阶段将它们作为可阅读资料。不能把 `SKILL.md` 的存在当作 Being 原生技能加载支持，也不自动改写 Being 的身份、记忆或共享系统提示。

如果之后决定实现单会话编排，Codex / Cursor / Grok 的差异应通过执行适配器承载。适配器负责检测版本及可用状态、启动参数、结构化事件转换和取消；任务记录、去重、工作区串行、结果通知与验收归属宿主，不能由每个插件各做一套。

接口可预留，但插件安装不会开启编排模式。首次实现先验证一个适配器；只有进程清理、取消和失败行为通过契约测试的适配器才可发布。多会话不在本设计中。

## 开放契约与兼容

Portal 的 `manifest.json` 保持原格式。未来界面信息使用独立的 `desktop.plugin.json`，可以与 Kit 同包，也可以单独发布。旧 Kit 没有该文件时仍按现有方式运行。

以下只是拟议格式，用于讨论；当前客户端不会加载它：

```json
{
  "schemaVersion": 1,
  "id": "community.scroll-reader",
  "name": "卷轴阅读器",
  "version": "1.0.0",
  "requires": { "pluginApi": "^1.0.0" },
  "license": "MIT",
  "capabilities": ["town.scrolls.public.read"],
  "contributes": {
    "panels": [
      {
        "id": "public-scrolls",
        "title": "公开卷轴",
        "component": "scroll-list",
        "source": "town.scrolls.public"
      }
    ]
  }
}
```

`source`、`component` 和 `capabilities` 必须属于宿主已实现的枚举，不接受任意请求地址、脚本或本机命令。能力声明只是请求，宿主逐次检查实际授权与当前连接。未实现的必需能力或不兼容的 API 主版本阻止激活，并解释原因。

插件 ID、发布来源和版本共同确定安装身份；本地开发目录与社区发布者不因相同 ID 自动合并。界面贡献使用插件 ID 命名空间。依赖 Kit 时明确指定 Kit 名称和版本范围，依赖缺失只禁用相关贡献。还应校验 Portal 实际的工具路由冲突，包括横线转换成下划线后的冲突。

公开 SDK 包含 JSON Schema、TypeScript 数据类型、宿主错误码、能力清单和生命周期文档。稳定 API 使用语义化版本；内部 IPC、DOM 结构及未发布接口不属于兼容承诺。先完成参考实现和契约测试，再发布 SDK 1.0，避免社区依赖尚未落地的规范。

## 插件宿主的职责

| 模块（拟议） | 职责 |
| --- | --- |
| Registry | 读取元数据，区分来源，检查兼容性、依赖和命名冲突 |
| Installer | 复用现有下载与暂存检查，记录固定版本和校验值，事务安装 |
| Host | 管理激活状态、数据授权、连接代次和插件私有存储 |
| UI renderer | 把声明转换为统一面板、卡片与设置表单 |
| Portal adapter | 映射到真实 Kit 运行时，识别外部管理的实例 |
| Worker adapter（可选） | 在编排范围确定后，接入宿主统一管理的 CLI 执行接口 |

界面插件获取经过筛选的数据对象，不拿凭据或任意 `fetch` / `exec` 能力。异步请求绑定插件版本、激活代次和 Being 连接代次；切换身份、停用或升级后取消旧请求并丢弃迟到结果。私有缓存按插件、账号和工作区分区，不把这些分区描述成服务端上下文隔离。

本机 Kit 本身是可执行程序。它的进程权限由运行时和操作系统决定，不能用界面插件的数据权限表来声称限制了 Kit 的全部文件或网络行为。依赖安装与运行授权需要在安装信息中说明，沿用现有具体安装流程。

## 用户管理与故障恢复

插件管理统一呈现“社区、已安装、本地开发”，但 Grove 仍是已有工具包来源。首批从 Grove 和本地目录开始；将来增加仓库来源时，先支持固定提交或发行包，保留来源、摘要和更新说明，不直接执行仓库默认分支的最新版。

安装前展示作者、许可、兼容版本、配置需求、依赖和会运行的程序。下载完成、依赖安装完成、已配置、工具可用分别记录。包摘要用于发现内容变化，不能替代发布者身份验证。Grove 未提供签名或可信摘要时明确记录验证范围。

更新先准备新版本并校验，待在途调用结束后切换；启动或迁移失败保留旧版本与配置。权限增加或启动命令改变不能静默继承旧授权。卸载只清理该插件拥有的内容；保留数据与删除数据分开处理，不删除共享依赖或外部管理的 Kit。

界面贡献按需激活，首屏聊天不等待社区插件。单个插件异常时撤销其界面和订阅，并展示可重试的错误；不会触发 Electron 重启。插件恢复不能自动重放有副作用的请求，连续启动失败后停止尝试。若未来 Worker 被纳入，应用重启后运行中的任务标记中断，不自动再次启动 CLI。

## 实施顺序与验收

1. **完善原生 Kit 管理**：展示已有元数据、配置缺项、认证说明和准确的管理归属。复用现有协议，不增加 Worker 或多会话。
2. **最小社区界面扩展**：实现声明式 manifest、Registry、只读 Host API 和一个公开卷轴示例，提供本地目录加载与校验工具。示例加载后不修改客户端核心代码即可增加入口，停用后入口与订阅一起消失。
3. **分发与兼容工具**：版本锁定、升级回退、示例仓库和贡献指南。离线契约测试覆盖未知能力、平台与版本不匹配、身份切换、权限撤销、命名冲突、故障隔离和更新失败恢复。
4. **按需求扩展**：隔离网页组件和 CLI 执行适配器分别评估。它们不作为前三步的隐式依赖，也不因社区 manifest 声明而自动开放。

测试默认使用离线服务和伪进程；单实例与进程清理测试复用现有 Electron 测试锁。测试界面读取不会向真实 Being 发消息，不启动付费 Agent 任务。实际 CLI 和 Windows 支持必须各自验证，不能从 manifest 的平台声明推断已经可用。

## 参考与兼容边界

Codex 的可借鉴之处是把可分发包、工具、使用说明和可选界面分开，并提供统一的安装管理体验，见 [官方插件架构](https://developers.openai.com/plugins/concepts/plugins) 和 [插件管理说明](https://learn.chatgpt.com/docs/plugins)。本方案的插件格式和客户端接口是 portal-desktop 的拟议设计，不宣称直接兼容 Codex 插件包、账号连接或其宿主 API。

如将来接入 MCP Apps UI，应先核对当时的标准以及 Portal 对资源和 UI 元数据的实际支持，再决定适配路径；当前 stdio 工具调用链本身不代表已经支持该界面协议。
