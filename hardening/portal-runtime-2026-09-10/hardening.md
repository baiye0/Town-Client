# Security Hardening Review: 精简、稳定、安全的社区 Portal

我们选择**方案 1：保留单个 Rust Portal，补齐明确的稳定性与安全缺口**。社区维护成本是首要约束：减少常驻组件、协议、配置项和外部依赖，每次修改都对应一个可复现问题。

Portal 的职责是连接 Being、执行用户允许的本地工具并返回结果。它不负责建设通用权限平台、管理虚拟机或替代操作系统服务管理器。完整取舍与验收见[精简技术方案](proposals/portal-runtime.md)。

## Evidence Basis

基线为 Portal `2dab52fc081d80a7bda9ce7735ab50c6cc6726ac`。已检查连接、执行、MCP/kit、平台守护与升级，以及当前桌面集成；29 份文件的身份和限制见 [context.md](context.md)。现有心跳、退避重连、单实例、后台输出环、kit 自恢复和升级回滚值得保留。

明确要修的路径包括：同步执行超时后的进程清理、完成后才截断的输出、阻塞请求与网络写入、任意 shell 与 workspace MCP 的权限说明，以及 Windows 本地更新候选执行前的真实性验证。这些是源码审阅结论，不是已完成的漏洞复现或跨平台测试。

## Constraints

- 默认一个普通用户下的 Rust Portal，进程内划分模块，不新增 broker/host/worker 常驻服务。
- macOS 复用现有 LaunchAgent/会话守护；Windows 复用当前 Limited 登录任务/守护。每个运行实例只由一个入口管理。
- 第一版聚焦登录用户模式，关闭 UI 不应影响独立后台安装。睡眠暂停、注销停止、权限不足按能力报错。
- 不默认新增 SQLite、任务调度服务、设备 PKI、通用 capability 令牌或自研沙箱。
- 接受通用 shell 就是授权该用户级别的代码执行；不宣传成 workspace 沙箱。新安装的执行能力由本地用户明确开启，旧用户配置不静默改写。

## Recommendation Summary

我们保留一个程序、一个配置文件、现有安装路径和 MCP 接口。代码内部共用三处逻辑即可：请求入口检查、子进程执行管理、运行状态记录。MCP/kit 原有子进程继续存在，但不再叠加自研执行器平台。

优先完成有界执行与取消，再统一各入口的权限检查和准确错误，随后补齐结构化状态及签名更新。网络故障只重连，单个 kit 故障只恢复该 kit，进程崩溃才交给守护器重启。命令效果不确定时明确报告，不自动重放；跨进程重启保存任务结果暂不承诺。

关于长期维护，我们要求修复附带针对真实故障的回归测试；新增依赖需解释它减少了什么代码和失败方式。成熟软件的身份、服务和更新机制用于借鉴，不能成为复制整套企业架构的理由。

## Next Decisions

后续按小 PR 推进：执行清理与资源上限 → 权限入口与安全默认值 → 状态/守护契约 → 签名升级与实机回归。只有用户明确需要跨重启结果恢复，才考虑一个嵌入式任务存储；只有明确需要注销后运行，才评估系统服务。当前不为这些假设预建框架。

本次修改仅收敛架构文档，未改运行代码。双平台稳定性仍以真实安装、断网、睡眠唤醒、崩溃、权限撤销及升级中断测试为发布依据。
